# XLeRobot-Mobile-Manipulation-With-Robo-MME

Memory-dependent mobile manipulation on [XLeRobot](https://github.com/Vector-Wangel/XLeRobot)
(sim + real), evaluated with π0.5. Uni Bonn, Robot Perception and Learning Lab.

This repo runs XLeRobot in **two simulators** on the Marvin cluster, so the two can be compared:

| | Part A: Isaac Sim / Isaac Lab | Part B: ManiSkill |
| --- | --- | --- |
| Simulator | Isaac Sim 5.1 + Isaac Lab 2.3 + LeIsaac (Apptainer container) | ManiSkill 3 + SAPIEN (conda env) |
| Robot model | XLeRobot body + official SO-101 arms (`tools/build_xlerobot_urdf.py`) | XLeRobot's ManiSkill model (SO-100 arms), vendored |
| Action | 17-D, same keys and units as the real robot | 16-D joint deltas (`pd_joint_delta_pos_dual_arm`) |
| Scene | `XLeRobot-Sandbox-v0`: table, objects, bins, cups, occluders<br>`XLeRobot-ReplicaCAD-v0`: the same ReplicaCAD apartment as Part B (section 3E) | `XLeRobot-ReplicaCAD-v1`: ReplicaCAD apartment |
| Data | LeIsaac HDF5 → LeRobot v3 dataset | – |
| Browser teleop | uses Part B's teleop page and input mappings | `xlerobot_sim/teleop_web.py` |
| Workspace | `ws_allocate xle_sim 90` | `ws_allocate xlerobot 90` |

`docs/ROBOT_SPEC.md` (generated by `tools/export_robot_spec.py`) lists the joints, dimensions,
base and action spaces of the real robot and of both sim models, read straight from the source repos.

Skip this if `/lustre/scratch/data/<user>-xle_sim/images/isaac-lab_2.3.0.sif` already exists.

```bash

# 4. LeIsaac scenes and robots (login node, ~130 MB)
```

### C. Browser teleop: drive it yourself with keyboard or Xbox gamepad

| Input | Action |
| --- | --- |

### D. SO-101 leader arm drives a sim arm

Your real SO-101 leader arm, plugged into your laptop, moves one XLeRobot arm in the Isaac sandbox.
Keyboard and gamepad keep driving the base, the head and the other arm.

1. Start the teleop as in 3C and copy the URL it prints.
2. On the laptop (needs Python 3 and `pip install pyserial`; a LeRobot env has it), with the leader plugged in:

   ```bash
   python leader_client.py "http://localhost:22874/?token=..." --port /dev/ttyACM0   # right arm
   python leader_client.py "http://localhost:22874/?token=..." --port /dev/ttyACM0 --arm left
   ```

   `leader_client.py` is [`scripts/leader_client.py`](scripts/leader_client.py); copy that one file to the
   laptop. Port names: Linux `/dev/ttyACM0`, macOS `/dev/tty.usbmodem...`, Windows `COM3`
   (`lerobot-find-port` finds it). `--fake` sends a slow wave instead, to test without the arm.
3. The page's status line shows `leader arm: right arm`. The script prints each joint's angle from
   the calibration pose: hold the arm in that pose and every joint should read about 0.

If the script stops or loses the arm for 0.5 s, keys and gamepad take that arm over again from where it is.

**Calibration.** Same chain as LeRobot teleoperation, with the follower simulated:
leader ticks → normalised value with the leader calibration `calibration/my_leader.json` (the value a
real follower would be sent) → sim joint angle with the follower calibration in
`xle_leisaac/robots/calibration.py` (`ARM_CALIBRATION_FILES`, `calibration/my_follower.json` for both
arms for now). That last step is the same conversion recorded data and the Joy-Con input (section 3F)
use, so all three agree. A value is turned back into the follower's servo ticks, and the
**calibration pose** (the pose held when LeRobot asks for "the middle of its range", which reads
2047 ticks) is sim angle 0, as in the official SO-101 `new_calib` model: angle = (ticks − 2047) · 360/4096.
The ends of each calibrated range are the sim joint limits, so these are usually not symmetric.
Note that LeRobot's value 0 is the middle of `range_min..range_max`, which is *not* the calibration
pose (on `my_follower.json` shoulder lift and elbow differ by about 20°). The gripper's 0..100 is
spread over the sim gripper's range (closed −10° to open 100°). A different leader file: `--leader_calibration`.

Check a calibration without a GPU (prints the sim angle at each end of every joint's range and at the calibration pose):

```bash
source env.local.sh && python3 tools/check_leader_mapping.py
```

### E. The apartment: XLeRobot-ReplicaCAD-v0

The ReplicaCAD apartment (the one Part B uses) converted to Isaac Sim: kitchen, living room,
about 100 movable objects, and furniture whose drawers and doors open (kitchen counter, fridge,
wall cupboard, chest of drawers, cabinet). Robot, cameras, the 17-D action, observations and
recording are the same as in the sandbox, so every command above takes `--task XLeRobot-ReplicaCAD-v0`:

```bash
bash scripts/start_teleop_isaac.sh --task XLeRobot-ReplicaCAD-v0 --device cpu
```

**Use `--device cpu`** with one environment. It runs the physics on the CPU (rendering stays on
the GPU). With ~100 resting objects that is 20x faster than GPU physics: about 21 env steps/s
in the apartment instead of 12, the same as the sandbox. GPU physics only pays off with many
parallel environments.

Check it (prints PASS/FAIL per line; pictures of every room in `logs/scene_check/`):

```bash
sbatch --output=$HOME/xle_scene_%j.out slurm/sim_job.sbatch \
    /isaac-sim/python.sh tools/check_scene.py --enable_cameras --device cpu
```

**How a scene is built.** `tools/build_replicacad_usd.py` (plain Python, login node) writes three
layers to `$XLE_ASSETS/replicacad/`, and `scenes/apt_0/manifest.json` lists what goes where:

| Layer | What | In Isaac Lab |
| --- | --- | --- |
| shell | walls, floor, fixed furniture, ceiling lights | one static USD |
| objects | bowls, books, cushions, ... | one rigid object collection, reset every episode |
| furniture | articulations with drawers and doors | fixed base; joints damped, so a drawer stays where it is left |

The manifest also holds the robot's start pose and named **anchors** for tasks: counter tops,
the inside of each drawer and cupboard shelf (`counter_left`, `drawer_left_top`, ...), each in the
frame of its furniture link. `tools/settle_scene.py` (run by the setup script) lets the objects
come to rest once in Isaac Sim and stores those poses, so episodes do not start with things
sliding into place.

**Another scene (e.g. a scan of the lab)** is another manifest: a shell USD, objects, furniture
and a robot start pose. Point a subclass of `XLeRobotSceneEnvCfg` (`xle_leisaac/tasks/scene_env_cfg.py`)
at it with `scene_manifest`, register a new id, and nothing else changes.

ReplicaCAD details the converter deals with (in case a scene looks wrong): Habitat's Y-up frames
are turned Z-up; per-instance furniture scale is baked into the furniture files (so drawer travel
is scaled too); each articulation's root link is made its asset origin (Isaac Lab places the root
link at the spawn pose on every reset); slightly tilted furniture is made upright; objects that
start sunk into a surface are lifted; room doors are left out, as in ManiSkill.

### F. Joy-Con in the lab (XLeRobot's own Joy-Con code drives the sim)

The lab laptop runs XLeRobot's real-robot Joy-Con teleop (`examples/7_xlerobot_teleop_joycon.py`)
**unchanged**, but sends its actions to the sim instead of the robot. The sim converts them with
the arm calibration in `calibration/`, so it reacts as the real robot would.

On the **lab laptop** (Linux, the same Python env you use for the real XLeRobot: `lerobot`,
XLeRobot's `xlerobot_model` + `lerobot_robot_xlerobot` plugins, and `joycon-robotics`):

1. Pair both Joy-Cons (XLeRobot docs: hold sync, pair in Bluetooth settings, press L + R).
2. On Marvin (VS Code terminal): `bash scripts/start_teleop_isaac.sh`, and wait for the URL.
3. On the laptop, open the tunnel the script prints (`ssh -N -L <port>:localhost:<port> ...`).
4. On the laptop, start the Joy-Con client with that URL:
   ```bash
   python tools/joycon_sim_client.py --url "http://localhost:<port>/?token=<token>" --xlerobot ~/XLeRobot
   ```
5. Open the same URL in the laptop's browser to watch the four cameras.

Controls are XLeRobot's, so they match the real robot:

| Joy-Con | Action |
| --- | --- |
| Right / left stick | right / left arm: up-down on the stick moves the end effector forward-back and up-down together; left-right turns the shoulder (pan) |
| R / L, and R-stick / L-stick click | arm up / down |
| ZR / ZL (hold) | gripper; each new press flips between closing and opening |
| Tilt the Joy-Con | wrist pitch and roll |
| Right X / B, Y / A | base: **X drives backward and B forward** in XLeRobot's code (its comments say the opposite); Y / A turn |
| Left D-pad | head |
| Right + | arms and head back to the zero pose (Home / Capture resets that Joy-Con's target) |

When the Joy-Con client stops, keyboard and gamepad on the page take over again.

Test without Joy-Cons (scripted fake Joy-Cons, inside a GPU job):
```bash
python tools/joycon_sim_client.py --url ... --xlerobot $XLE_THIRD_PARTY/XLeRobot --fake --seconds 20
```

## 7. Robot model in one paragraph

The body, cart, neck and head come from XLeRobot's own model (`simulation/Isaac_sim/xlerobot.zip`).
The two arms are the official SO-101 `new_calib` model from TheRobotStudio/SO-ARM100, with
its wrist-camera mount, mounted where XLeRobot's arms sit. The base moves on three virtual
joints (x, y, turn), like LeKiwi in LeIsaac.

The 17 actions have the same names and units as the real robot:
- `left_arm_*.pos`, `right_arm_*.pos`, `head_motor_1/2.pos`;
- `x.vel`, `y.vel` in m/s;
- `theta.vel` in deg/s.

Motor limits are the real STS3215. The total mass is 12 kg. Pinned versions are in
`versions.lock.md`.

## 8. Training π0.5 with or without memory

`xle_policies/pi05_mem` is LeRobot's π0.5 with one switch, `--policy.memory`:

| `memory=` | What the policy sees |
| --- | --- |
| `none` | the current frame only: LeRobot's π0.5 unchanged |
| `framesamp_modul` | RoboMME's best variant, **FrameSamp + Modul**: 32 past head-camera frames, sampled evenly over the episode so far. Each one is pooled to 16 SigLIP tokens. In every action-expert layer, cross-attention to them gives an AdaLN scale and shift before the feed-forward. It adds ~88M parameters; the VLM is untouched. |

Both use the same training settings, and the vision encoder is frozen for both, as in
RoboMME. Other designs go into `MEMORY_TYPES` in `configuration.py` and a builder in
`memory.py`. The port follows RoboMME's code (`RoboMME/robomme_policy_learning@ac846a9`).
`tools/test_pi05_mem.py` checks it against that code and checks that the training and
inference paths match.

```bash
bash setup/05_pi_deps.sh          # once: the patched transformers LeRobot's π0.5 needs
# once per dataset, memory runs only: SigLIP features of every head-camera frame (~64 KB/frame)
XLE_WITH_PI=1 sbatch --output=$HOME/xle_cache_%j.out slurm/sim_job.sbatch \
    /isaac-sim/python.sh tools/build_memory_cache.py --repo_id local/xle_sandbox_v0
sbatch slurm/train_pi05_mem.sbatch none               # baseline
sbatch slurm/train_pi05_mem.sbatch framesamp_modul    # memory
```

- **Hugging Face access.** π0.5's tokenizer (`google/paligemma-3b-pt-224`) is gated. Accept
  its licence on Hugging Face, then log in inside the container (`HF_HOME` is set there).
- **Same weights for cache and training.** Cached and online memory features must come
  from the same vision weights. Build the cache from the checkpoint you fine-tune from.
- **Inference.** Call `select_action` at every control step, at the dataset's fps. It
  encodes each frame into the memory buffer, and `reset()` clears the buffer between
  episodes.
- **Lustre.** The root of the `xle_sim` workspace refuses new files (ENOSPC: their first
  256 KB go to a full metadata server). Subfolders work; `05_pi_deps.sh` sets an
  OST-only layout for its folder.

## Teleop in simulation

```bash
bash scripts/start_teleop.sh                        # 1 h on mlgpu_devel (A40)
PARTITION=mlgpu_short TIME=04:00:00 bash scripts/start_teleop.sh   # longer session
```

The script submits a GPU job and waits until the scene has loaded (usually under a minute). It then
starts a small relay on the login node (`scripts/relay.py`, localhost only) and prints a URL:

```
 Open in your laptop's browser:   http://localhost:22874/?token=...
```

1. Run the script from the **VS Code terminal**. VS Code forwards the printed port from the login node
   to your laptop. If it doesn't show up in the **Ports** tab, add the port number there yourself.
   The port is `20000 + your uid % 20000` (22874 for `s24imoha_hpc`). If it's taken, the next free one is used.
2. Open the URL. Click the page so it captures the keyboard. The robot stops when the page loses
   focus, when you press Esc, or when the browser stops sending input for 1 s.
3. When you're done, run `scancel <job>`. The relay stops on its own when the job ends.

Run the script from the terminal on the login node, not from your laptop. Without VS Code, use the
`ssh -N -L ...` command it prints in a terminal **on your laptop**.

The page shows a chase camera, the head camera and both wrist cameras. It runs at about 30 Hz.
Keyboard and gamepad can be used at the same time. **Arm 1 is the robot's right arm, arm 2 its left.**

### Gamepad (Xbox)

Connect the controller **to your laptop** (USB or Bluetooth). Open the page in Chrome or Edge, then press
any button on the controller. The header should say `gamepad: Xbox ...`. This uses the browser's Gamepad
API, so nothing is installed on the cluster. Any controller the browser reports with the `standard`
layout works the same way, e.g. PlayStation or Switch Pro.

| Gamepad | Action |
|---|---|
| D-pad | base forward/back, turn left/right |
| Right stick | arm 1 (right) end effector up-down / forward-back |
| RB + right stick | arm 1 wrist pitch / roll |
| R3 (click) + right stick | arm 1 shoulder rotation |
| RT | close gripper 1 (analog: release to open) |
| Left side (stick, LB, L3, LT) | the same for arm 2 (left) |
| X / B, Y / A | head pan left/right, tilt up/down |
| Menu (≡) | reset arm targets |

The layout follows upstream's `demo_ctrl_action_ee_xbox.py`, with two fixes: each trigger now closes the
gripper on its own side, and the base is driven with the D-pad.

**Joy-Con (planned primary device):** this isn't implemented yet. Untested Joy-Con input is safer to
build once the hardware arrives. When it does, pair the Joy-Cons with your laptop, open the page and tick
**raw gamepad**. The panel shows the layout and button numbers the browser reports, and that's what
the Joy-Con mapping will be built from.

## Notes

- **GPU:** the `mlgpu_*` partitions have A40s, which support graphics and ray tracing. The `sgpu_*`
  A100s can render the default shader but have no RT cores. Physics runs on the CPU for a single env.
- **Versions:** mani-skill 3.0.0b21, sapien 3.0.3 and torch 2.15 (CUDA 13). Marvin's driver is 580,
  which supports CUDA 13.0.
- **Upstream pygame demos** (`third_party/xlerobot_maniskill/examples/`) open a local window and the
  SAPIEN viewer. They need a real desktop session, so they don't run in a plain Slurm job.
- **Changes from upstream:** the third-person camera follows from behind instead of facing the robot.
  Key X keeps the base heading instead of turning the robot back to 0. Grippers start open, and keyboard
  V/B toggles them closed.
